TASK 22 — ORIGINAL AI-CPS BALL CATCHING (protocol notes v2)

Scene and objective
- You operate a fixed-base Franka Panda already holding the blue catching tool. The target is the moving red sphere, radius 0.01 m, mass 0.001 kg. Intercept it with the tool opening, then keep it inside through the remaining episode. There is no navigation, grasp-tool phase, automatic catcher, reset or respawn tool.
- Upstream reset places the ball at approximately [-0.8, 0, 1.5] metres with independent x/y offsets in [-0.05, 0.05]. In this evaluation profile its reset velocity is [1, 0, 0] m/s and gravity is [0, 0, -9.81] m/s^2. These are reset parameters, NOT the current state: initialization already advances physics. Read the actual ball position and velocity in every callback.
- The nominal tool root starts near [-0.05, 0, 0.88] m. Its root, catching centre and robot flange are different frames. The observed catching centre is the task's center_cube reference. Never substitute a remembered flange offset for this measured centre.

Frames and measurements
- The robot root is translated to [0.3, 0, 0] m and has quaternion [0, 0, 0, 1] in wxyz order: a 180-degree rotation about world Z, NOT identity. For a point expressed in that robot-root frame, world xyz = [0.3 - base_x, -base_y, base_z]. Convert Jacobian translation directions with the same rotation. An arbitrary DH convention may have an additional frame offset; verify it before trusting it.
- Let n = obs['native_observation']. Ball xyz = n[18:21]; catching_centre_minus_ball = n[21:24]; ball velocity = n[24:27]. Therefore measured catching centre = ball xyz + catching_centre_minus_ball. A positive x difference means the tool centre is to the world's +X side of the ball. These values are in world coordinates and metres, not camera pixels or robot-root coordinates.
- Prefer obs['joint_positions_rad'], obs['joint_velocities_rad_s'] and obs['joint_targets_rad'] for the seven arm joints. Native n[9:18] is the NINE joint velocities multiplied by 0.1 for this task; finger velocities are prismatic. The exported native array is clipped to [-5,5], so saturated values are not exact unbounded measurements.
- Ball/catching-centre state is available each control tick. No measured tool orientation, Jacobian or contact-retention flag is exported in this interface. If your controller needs these quantities, distinguish kinematic estimates from measurements and check them against the allowed observations.

Control and feedback workflow
- Available robot tools: observe, move_joints, coding_control. observe reads state/images without advancing physics. move_joints repeats the SAME seven normalized target increments for its requested number of steps; it does not execute an absolute joint pose. coding_control calls your control(obs, memory) at each ~1/60 s tick and can adapt the seven increments using fresh numeric feedback.
- The fingers are held at the original task's fixed targets. You cannot close a gripper around the ball. Seven arm joints move together, with native limits, position drives, inertia and the original independent action noise (std 0.5). Last-step noise is observable after the fact; future noise is unknown.
- The first interception opportunity is much shorter than the full five-second episode. Use the observed ball height/vertical velocity and gravity to estimate a future crossing of a reachable catching height, then consider horizontal position, arm travel time and keeping the opening oriented to receive the ball. Chasing the current ball position with a delayed or unverified coordinate mapping can miss this opportunity.
- You may write and check your calculations in the isolated shell while physics is paused. python3 and standard-library math are available; do not assume a python alias or NumPy. A large probing segment consumes real interception time once executed. Prefer minimal, bounded frame checks, then a per-tick controller with damping, joint-limit handling and compensation for drift in previous joint targets. No ready-made controller is supplied.
- After interception, maintain containment and suppress relative motion rather than stopping at one small XY error. If a short segment reveals a wrong sign, diverging error or loss of the ball, return done=true to hand control back to the model without another action. This ends only that segment. Changing programs clears memory; carry any calibration explicitly into the next program.
- The tool returns images at interaction boundaries (current plus sampled history); code callbacks receive current numeric feedback, not a newly requested image every tick. Video independently records every control step.

Evaluation and termination
- Budget: 300 native control steps, ~60 Hz, two physics substeps per action. Original reset/termination counting currently ends after 298 policy actions and yields 299 trace samples. LLM reasoning and shell computation do not consume simulation time; code callbacks do.
- The upstream STL formula is always[50:299](XY catching-centre-to-ball distance <= 0.1 m), using trace-sample indices, not seconds. The upstream scorer takes the minimum returned robustness and requires it to be strictly positive. This is an evaluation description, not a live score oracle.
- This XY-only predicate does not certify vertical containment. A ball on the floor can be close in XY to a tool above it. Likewise tool success=true reports that a command executed, not that the ball was caught. Continue attempting the physical goal until native termination; do not reset, edit physics, remove noise, query hidden scoring or end the episode by asserting completion.
