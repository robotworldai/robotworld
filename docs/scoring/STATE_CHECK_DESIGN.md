# 状态检查设计 v0.3（已实现为 World state v1）

环境定义“考什么、如何施加扰动、何时结束”，success定义“哪些状态需要成立”。同一个检查器概念可以用于不同benchmark；机器人状态仍由各bench适配器计算。

| 类型 | 语义 | 例子 |
|---|---|---|
| `final(P)` | 在约定结束时刻T检查P | 路线已完成；有效回球数≥3 |
| `hold(P, N)` | 最后N秒 `[T-N,T]` 中P始终成立 | 在终点低速站稳2秒 |
| `always(P, window)` | 事先固定的整个窗口中P始终成立 | 搬运全程物体未掉落 |

P可以是几个物理量的AND，也可以是由真实轨迹得到的状态。时间按模拟时间计算；不能把零散达标帧相加，中断后也不能回补过去的保持时间。窗口起点在环境设置中固定，不能事后挑选表现好的一段。

## 分工

- **环境设置**：资产、初态、路线、命令轨迹、力/速度扰动、随机seed、动作周期、步数上限、固定评测时刻。原生失败和新增场景边界也在此声明。
- **状态提取**：从允许评测端读取的真实物理轨迹计算位置/速度/姿态/接触，或更新路线完成、起跳后落地、有效击球等事件状态。保持坐标系、单位、接触对象和边界比较明确。
- **目标检查**：仅调用上述三类检查，每题1～2条。
- **结果有效性**：施力器、资产或传感器故障单列invalid；模型先摔倒不能因此改列invalid。已删除的接触异常退让题不再进入活动题集。

有效回合中，没有原生/已声明场景失败且所有目标检查成立，才记World success。原reward、原子回合成功率与额外状态分别保存，不强制把连续reward阈值化。新判据不是官方SR。

## 过程不是只看最后一帧

`route_complete`按有向门顺序从轨迹更新；`completed_jumps`只在真实起跳、达到声明高度并落地后累计；颠球复用原`num_height_hits`。这些可以在结束时检查，但不能由LLM自报，也不能在重置后累计拼接成绩。搬运是否中途掉物应使用`always`，不能用终点时物体重新在托盘上替代。

新状态不得额外泄露给policy；模型继续只使用公开目标和允许的观测。上游不存在的过程状态需要外部World适配器实现与验证，不能只改字段名称就当成已有功能。

## 本次设计变化

Go2等到点任务删除逐次扰动恢复限时，仅检查末段到点停稳；Digit和倒立摆用固定完整窗口代替多个时间比例；颠球直接用原高度达标弧线计数，取消“前4段必须全部达标”的额外序列。这些是目标设计变化，不是单纯把旧复杂条件藏在一个布尔变量里。

所有新增容差、时长、路线和事件数量仍需校准。尤其全程成立比时间比例达标更严格，必须用可行参考控制器确认。上游源码保持不变；checker及World外部场景层已上线。261个构造状态正反例和16项Docker状态读取已通过，但尚无每题的物理成功轨迹。详见[实现与验证](IMPLEMENTATION.md)。

当前在重置及每个控制步采样，不逐物理子步检查。控制步之间的瞬时违例不能由此保证被捕获。
